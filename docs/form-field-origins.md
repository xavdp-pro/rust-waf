# Form field origin and qualified exception API

A site exception may add optional `form_field`, a 1–64-byte ASCII alphanumeric/underscore name. Omission or null retains the original route/method exception and canonical fingerprint; a field declaration changes the fingerprint and must reference a body-target rule. A field exception is never returned by the route-only exception lookup.

The scanner selects original form values using one strict URL decoding of the name. Original `&`/`=` boundaries identify values; percent decoding of a value never creates a new parameter origin. Selected scalar duplicates, including encoded name aliases or valueless duplicates, remove that binding. Only configured names consume metadata, regardless of unselected parameter count. Complete raw and decoded body views are still inspected and validated; forwarded bytes never change. Decoded-view span offsets follow changes in byte length, including Unicode and later lossy decoding. No body views or values are retained in a completed scan.

For a field-target rule, ordinary matching establishes the minimum match start. A separately compiled Thompson PikeVM in all-match mode scans through EOF to establish the maximum possible match end, ignoring alternative/greedy priority. The candidate field must cover this complete match hull in every body view. This includes later sibling occurrences, overlapping occurrences and longer alternatives at the same start. Searches are linear in input length for a fixed automaton, without enumerating every possible start or retaining match spans. The automaton has a one-MiB compilation bound and implicit captures only. Its per-request cache is allocated lazily and reused between views. Compilation failures and patterns with any zero-length match prevent startup; matcher disagreement prevents forwarding.

`Inspector::inspect_scanned_with_fields(request, effective_method, confirmed_fields)` requires the application adapter to confirm a scalar binding and actual consumer. Default inspection confirms nothing. Query, path, header or unattributed-body matches cannot borrow the form exception. Route/method scope and rule/profile provenance remain enforced. Successful exception matches retain their declaring profile, and their high-confidence flag cannot start a ban because the existing proxy excludes excepted matches.

Application confirmation is not a client header. The adapter must independently validate its parser's key normalization, arrays/collisions, selected action, alternative dispatch and actual method. The shared engine's name semantics deliberately do not invent PHP normalization. WordPress can now confirm pwd on explicitly evidence-bearing site login consumers; default profiles still confirm nothing. An exception alone cannot weaken inspection, including when a client sends a forged confirmation header. No generic password exception is enabled automatically. See [the consumer contract](../crates/waf-wordpress/README.md).

Current scope is one uniquely bound URL-encoded scalar field covering all occurrences of a rule. Separate matches in multiple otherwise qualified fields remain unexcepted; JSON/multipart bindings and partial-exception statistics need further implementation and qualification. This checkpoint is a prerequisite, not completed site compatibility. Do not enable a site rule until actual consumer, positive/negative method/dispatch/permission cases and resource measurements qualify it. Complete the broader field/visitor requirements before full acceptance.

Tests cover canonical/encoded names and values, decoded separators, UTF-8/lossy offsets, duplicate/valueless bindings, double-encoded names, cross-field and same-start alternatives, Unicode boundaries, a 256-KiB repetitive greedy case, zero-length startup rejection, all seven starter automata, query/header/route/method isolation, non-form bodies, syntax/depth failures and bounded metadata with 100,000 unselected parameters. Diagnostic decoding is compared with complete legacy views and error codes. A neutral protocol group proves field configuration and a forged header still receive correlated pre-backend denials without adapter confirmation.

Reproduce using `cargo test --workspace --locked`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo fmt --all -- --check`, `python3 tools/check_repository.py` and `python3 observability/evaluate_waf.py --self-test`. These tests are authored implementation fixtures, not independently labeled application effectiveness, actual WordPress password authentication, browser workflows or deployed concurrent resource acceptance.
